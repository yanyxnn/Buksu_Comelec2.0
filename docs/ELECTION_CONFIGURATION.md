# ELECTION CONFIGURATION

## Creation workflow
Create Election → Basic Information → Template (optional) → Scope → Contests → Voter Eligibility → Candidate Eligibility → Candidates/Parties → Ballot Rules → Abstention → Schedule → Results/Reporting → Preview → Eligibility Test → Validation → Approval → Configuration Snapshot → Lock → Schedule/Open.

## Templates
The four supported templates are University-Wide, College / Department, Year Representative and Sectoral, plus a future “Create from Previous Election”. “Customize from scratch” is not a template: it stores `NULL` in `template_key`. A template is a starting configuration only, and template contents are not yet defined.

## Phase 04A: draft creation
An administrator creates a draft from `/admin/elections/new` with a name, optional description, an election type and an optional starting template ("Customize from scratch" stores none). One transaction creates the election in `DRAFT`, version 1 (`DRAFT`, `config_json` NULL) and links `current_config_version_id`. Type (what kind of election) and template (which starting point) are separate fields; a template pre-fills nothing yet (see `OPEN_DECISIONS.md`). `/admin/elections/{election}` reopens a draft read-only, showing saved details and configuration status. Eligibility, candidates, ballot rules and the schedule are later steps (scope is Phase 04B, contests Phase 04C).

## Phase 04B: scope (representation groups)
The Scope step of the creation workflow is realized as representation groups on `/admin/elections/{election}/scope`. A group has a name and a `scope_definition_json` of administrator-configured dimensions (key -> list of values); the application supplies no dimensions or values. Groups organize contests; they are not voter or candidate eligibility rules, which are separate, later steps. Scope can be read in any state and edited only while the election is an editable draft (state `DRAFT`, nothing locked, current configuration version a `DRAFT` with no frozen JSON); editing in `READY` is an open decision. A group used by a contest cannot be deleted.

## Phase 04C: contests
The Contests step is managed on `/admin/elections/{election}/contests`. A contest has a name, a position label, an optional representation group (only a group of the same election) and one voting rule: seat count, maximum selections per voter, whether abstaining is allowed, and the voting method (`SINGLE_CHOICE` or `MULTI_CHOICE`). Contests are bound to the election's current configuration version and can be created, edited and deleted only while the election is an editable draft (the same conditions as scope: state `DRAFT`, nothing locked, current version `DRAFT` with no frozen JSON); in any other state the page is read-only. Seats and the selection limit are separate settings and no relation between them is applied (a multi-seat contest may allow fewer than the maximum selections; see `DATABASE.md`). A contest with dependent records (eligibility rules, candidacies, ballot responses, results) cannot be deleted. No contest list, seat count or eligibility rule ships with the application, and `contests.scope` is not used.

## Election configuration screens: wording and category names
The scope and contest pages are written for administrators rather than for the database. On the scope page a dimension is called a **category**: the administrator types an ordinary name (for example "Representation Type") and the application generates the internal lowercase underscore key (`representation_type`) with Laravel's string helpers; a name that would start with a digit gets a `category_` prefix, and a name with no letters or numbers is refused. Two names that become the same key are refused as duplicates. Saved keys are shown as readable names in the group list and when a group is edited, and a key that its readable name cannot reproduce exactly (for example one containing a double underscore) is saved back unchanged unless the administrator renames that category. The stored `scope_definition_json` structure is unchanged: a map of key to a list of text values, entered one per line. The contest form is organized into "Contest details" and "Voting settings" with a help line under each field, and explains that available seats and the maximum candidates a voter may select are separate settings and that a representation group organizes a contest without determining eligibility. These are wording and layout changes only: no election policy, validation rule, institutional category, value, seat count or eligibility behavior is introduced, and the services, authorization, audit logging and database schema are untouched.

### Election configuration redesign (workspace, representation groups, contests)
The three configuration pages share one look (BukSU purple and gold), one navigation bar (Workspace, Representation groups, Contests), and one feedback pattern. This is a presentation and usability change; the services, policies, audit logging, transactions, locking and schema are unchanged.

* **Election workspace** is the read-only overview of one election: header with state badge, election type and an "Editable draft" or "Read-only" indicator; two step cards (representation groups, contests) with the saved counts and a Configure or View action chosen by the existing authorization and editability rules; the saved details; and the configuration status (state, current version, whether configuration content has been snapshotted, locked version). It shows no readiness score, percentage or approval, and it states that voter eligibility, candidate eligibility, candidates, ballot rules, scheduling and results are separate stages.
* **Representation groups**: the values of a category are added one at a time (Add button or Enter), shown as tags that can be edited or removed before saving, and a value typed but not yet added is added when the group is saved. Browsers cannot paste several lines into the input, but a pasted block of lines on the server adds one tag per line. Internally the form still holds one value per line and the saved `scope_definition_json` is unchanged: an object of internal category key to a list of text values (at most 100 values of at most 255 characters per category, as before). Internal keys stay hidden; the key generation and `storedKeys` round-trip rules are as described above. Saved groups are cards showing the categories, the values as tags and the number of contests using the group.
* **Contests**: a guided flow of Contest details, Voting settings and Review before saving. The review validates the form and shows exactly what was entered, including the representation group name, the available seats, the maximum candidates a voter may select, the voting method and the abstention setting; it saves nothing, and only its Save button writes through the service. `name` and `position_label` remain separate fields, and no relation between seats, the selection limit and the voting method is introduced.
* **Feedback**: Save buttons show "Saving..." and are disabled while the request runs; success toasts ("Representation group created successfully.", "Changes saved successfully.", "Contest deleted successfully." and so on) are shown only after the service transaction completed, and the same message is placed in an `aria-live` status region for screen readers; toasts respect reduced-motion settings. Editing shows an "Editing" indicator with the record name, a "Save changes" action and a Cancel action. An "Unsaved changes" indicator appears once a field is changed, and the browser warns before leaving the page (including Livewire navigation) or cancelling with unsaved changes. Deletion asks for confirmation in a dialog that names the group or contest and explains that deletion is blocked when it is in use or has dependent records; the blocked cases are refused with a message instead of opening the dialog. Failed operations show a plain message and keep what was typed. The notification pattern is page-local (a browser event and an Alpine toast); no notification backend was added.

## State machine
DRAFT → READY → APPROVED → SNAPSHOTTED → LOCKED → SCHEDULED → OPEN ↔ PAUSED → CLOSED → RECONCILING → RESULTS_PENDING_VALIDATION → VALIDATED → OFFICIALLY_ANNOUNCED → FINALIZED.

## Locking
Before OPEN, ballot-critical configuration is editable through controlled workflow. Once locked, normal edits are disabled. Exceptional changes require a change request, reason, independent approval, new version/snapshot, and revalidation as applicable.

## Election clock
Backend/server time is authoritative. Frontend countdown is display-only. Timezone: Asia/Manila unless institutionally changed and documented.

## Historical record
Every finalized election keeps its final configuration snapshot and immutable results as historical data.
